# 採集效能與正確性

目前任務狀態與優先順序統一維護在[專案狀態](project-status.md)；本文保留實作邊界和測量證據。

## 已實作的最佳化

1. 檔案解析快取按 mtime、ctime、檔案大小和相依檔案指紋重複使用結果。未變化時不序列化、不重寫快取；變化時先寫暫存檔再原子替換，失敗後可重試，快取故障不阻止採集。
2. 完整正規化結果按日期計算簽章，儲存在 `collection_checkpoints` 中，裝置與來源分別隔離。無變化時跳過用量表讀取和寫入；變化時讀取對應日期的日彙總、事件，以及相容工作區統計。其他日期的專案活動透過資料庫彙總保留，不載入其全部事件。
3. `GET /api/collect/status?wait=1` 在執行期間最多等待 25 秒，結束或失敗時立即回應。中斷連線會取消訂閱；逾時回傳目前狀態，用戶端繼續等待。一般狀態介面仍立即回傳，驗證規則不變，舊服務忽略參數時用戶端有退避保護。

採集仍記錄每個來源的執行狀態。輸出中的 `unchanged` 表示正規化輸入未變化；`reconciled_dates=N` 表示本次核對了 N 個變化日期，而不是僅保留了 N 天歷史。

## 可靠性邊界

- 日期簽章包含事件身份、日期、模型、專案、各項 token 和費用中繼資料，不能只比較總 token。補入舊記錄、改動中繼資料、事件跨日期移動都會觸發核對。
- 核對和寫入在同一交易中完成，費用保留策略與完整核對相同。簽章只有在資料成功提交後才生效；解析快取先更新也不會使失敗的資料庫寫入被跳過。
- SQLite 使用寫交易；PostgreSQL/MySQL 使用每個裝置/來源固定的進度列鎖。公用寫入方法、匯入、遷移和還原會在同一交易使該來源簽章失效。失效保留進度列，以便首次採集也能與並行匯入互斥。
- 無簽章、格式不相容、簽章損壞或一次變化超過 180 個日期時使用完整核對。修改核對語意時應提升簽章版本。`--dry-run` 和 `--full` 預覽始終走完整核對。
- 日誌刪除或輪替不會自動刪除已入庫歷史。清理舊記錄仍需明確的全量替換和備份流程。
- 簽章只是可重建的最佳化狀態，不能用於同步確認。直接在應用外修改資料庫時，需使對應進度失效後再採集；不要把進度表從另一份資料庫單獨複製過來。

目前仍會發現檔案、載入解析快取、正規化完整的採集輸出，並計算日期簽章。Codex 預設經過完整前綴校驗後續解析，Claude 預設完整解析變化檔案；兩者另有下述可選的只追加位元組續讀模式。同步已改為交易變更記錄，沿用現有 HTTP 上傳協定。頁面查詢的後續最佳化見[大範圍查詢與按需明細](query-performance.md)。Codex 的累計用量、Claude 的串流修正以及跨檔案去重必須在進一步增量化時一起處理。

## 基準方法與結果

2026-09-26，在同一台 macOS 機器上與 `9a58c22` 比較。使用獨立資料庫、獨立解析快取；冷啟動和簽章建立不計入下面的熱快取結果。每個場景交替執行兩個版本各 5 次，取行程完整執行耗時的中位數，不包含頁面重新整理。

| 場景 | 修改前 | 修改後 |
| --- | ---: | ---: |
| Codex 單來源，無變化 | 521 ms | 321 ms |
| Codex 單來源，追加日誌 | 523 ms | 361 ms |
| Codex 單來源，補入歷史記錄 | 538 ms | 362 ms |
| 全來源，無變化 | 1,157 ms | 742 ms |

Codex 三種場景使用 446 個日誌檔案的固定副本，並追加受控測試記錄；每輪三張用量表逐列比對一致（排除執行時間戳與鎖定時間戳）。全來源測試讀取本機日誌、寫入資料庫副本，最終 927 個日彙總、80,934 個事件、1,186 個相容工作區統計在兩個版本間一致；欄位核對僅有浮點費用約 `7.1e-15 USD` 的差異，低於 `1e-9 USD` 的金額比對容差，其他業務欄位一致。

這些資料是本機樣本，不代表所有裝置或遠端資料庫的耗時。首次執行仍需建立簽章，大範圍日誌變化仍會完整核對。頁面完成通知移除原來的固定 1.5 秒輪詢間隔，頁面查詢及渲染耗時需單獨觀察。

## Codex 解析續接

Codex 解析快取儲存已完成列的位元組位置、SHA-256、原始事件和解析狀態（模型、工作區、累計用量、工作階段身份、turn 與 fork 重放狀態）。檔案變化後，校驗已消耗前綴全部位元組，相符時只解析新列；舊內容被修改、檔案截斷或快取版本變化時完整解析。不能用頭尾抽樣代替完整校驗，否則中間改寫後追加會漏算。

末列沒有換行時，仍按原解析器語意顯示可解析事件，但不提交其解析狀態；下一次重新解析末列，避免半列 JSON、UTF-8 字元或補換行造成重複。解析狀態不包含費用，資料庫原有費用保留策略不變。`PARSE_CACHE=0` 可繞過快取。

2026-09-26 的合成測試：63.76 MB Codex 日誌追加 138 位元組，交替執行完整解析與續接各 5 次，中位數分別為 56 ms 和 46 ms（約減少 18%）。這僅是當時單檔案解析耗時，不是整次採集耗時，也不代表真實日誌的普遍收益。預設模式仍包含完整檔案讀取和 SHA-256 校驗，快取事件仍需正規化。

## Codex 可選位元組續讀

預設不改變可靠性邊界。只有能保證 Codex 日誌舊內容不被原地改寫時，才在採集行程設定 `CODEX_LOG_APPEND_ONLY=1`，並保持 `PARSE_CACHE` 開啟。也可在本機 `.env` 設定；本輪沒有替使用者開啟。切換該選項會更新快取版本、重建完整基線，關閉後還原預設全前綴校驗。其他採集器不受影響。

可選模式儲存檔案身份、觀察到的長度、最後完整列偏移、解析狀態及檢查點校驗和。正常追加只從完整列偏移讀取到本次開啟時的檔案長度；末尾半列會重讀，後續追加留給下一次採集。檔案替換、觀察到的縮短、同長度但中繼資料變化、檢查點損壞或版本改變時重新讀取並解析。讀取期間觀察到截斷或改寫時本次採集失敗，下一次重新核對，不儲存混合檢查點。

這些檢查不能識別「改寫歷史中部後繼續增長」，也不能識別兩次採集之間截斷再增長到原長度以上的所有情況；這正是明確只追加限制的用途。檢查點校驗和防意外損壞，不是防惡意篡改。不能把此選項作為任何日誌都安全的預設加速開關，也不因此把原始通用 READ-01 標為全部完成。

2026-10-04，在同機合成 64 MiB 日誌上追加 157 位元組，兩種模式各啟動 3 個新行程讀取持久檢查點。預設模式實際讀取 67,109,262 位元組，可選模式讀取 157 位元組；兩者均只向解析器傳入 157 位元組，最終事件逐項一致。檔案處理耗時中位數約 59.8 ms / 8.0 ms，其中解析約 7.8 ms / 7.4 ms；行程峰值 RSS 中位數約 116.5 / 51.4 MiB（包含 Node 執行階段）。此樣本只有少量用量事件，不代表大事件快取的整體收益，也不是整次採集基準。可執行 `node --test test/parse-continuation.test.mjs test/parse-cache.test.mjs` 驗證讀取位元組數、重新啟動及回退語意。

## Claude 可選位元組續讀

`CLAUDE_LOG_APPEND_ONLY=1` 將同一讀取機制用於 Claude Code 的 projects/transcripts JSONL（包括已設定的桌面本機工作階段目錄）。預設保持完整讀取和解析變化檔案；無需修改預設行為即可偵測舊內容改寫。可選模式要求 `PARSE_CACHE` 開啟，與 Codex 開關獨立；切換模式會重建基線。沒有修改使用者現有 `.env` 或替使用者開啟開關。

檢查點保留每條原始用量快照和絕對列號，再按工作階段、訊息和請求合併最大值。這樣後續追加的串流修正和 advisor 用量可以更新舊回應，缺少訊息 ID 的同時間回應仍然獨立。跨檔案及 sidechain 去重在完整候選集合上執行。半列只參與本次顯示，不會污染已提交記錄；下次補齊或修改半列後重新解析。合併操作不修改檢查點中的物件。

檔案替換、可觀察截斷、同大小中繼資料變化、檢查點損壞沿用共用讀取器的回退；仍不能偵測中部改寫後增長或未觀察到的截斷再增長。因此通用 READ-01 仍為部分完成，未將其餘採集器位元組增量化。解析快取仍需完整載入、序列化和合併；重複串流快照多時，可選快取會比預設合併後記錄更大。此最佳化減少日誌讀取和 JSON 解析，不保證總耗時只隨新增位元組增長。

`node --test test/claude-continuation.test.mjs test/collector-accuracy.test.mjs test/parse-continuation.test.mjs` 涵蓋新舊解析結果一致、跨次修正、advisor、無 ID 列、UTF-8 半字元、未提交末列回退、重新啟動、模式切換、損壞快取以及已有採集準確性契約。

2026-10-04，macOS arm64 / Node 22.22.2，兩個模式各執行三個新行程，取耗時及峰值 RSS 中位數。完整模式讀取檔案並解析合併；續讀模式包含從磁碟讀取/反序列化持久檢查點、讀取新增位元組及合併記錄。計時不含掃描目錄、寫回快取、資料庫或整個採集鏈；系統檔案快取未清空。最終記錄摘要逐項一致，續讀位元組由 `onRead` 計數。

| 合成日誌 | 新增 / 續讀位元組 | 完整 / 續讀耗時 | 完整 / 續讀峰值 RSS |
| --- | ---: | ---: | ---: |
| 64 MiB 正文、2 條用量快照 | 199 / 199 | 39.19 / 0.94 ms | 193.06 / 44.62 MiB |
| 64 MiB 正文、4 萬條快照（約 72 MiB 檔案） | 205 / 205 | 82.48 / 62.49 ms | 233.75 / 146.34 MiB |
| 僅 4 萬條快照（約 7.8 MiB 檔案） | 205 / 205 | 41.55 / 58.63 ms | 95.97 / 146.22 MiB |

4 萬條快照合併成 1 萬條回應，續讀檢查點約 8.7 MiB。最後一種場景續讀反而更慢且更佔記憶體，說明不能把「僅讀新增日誌位元組」解釋成普遍更快。該模式更適合正文大、用量快照稀疏且保證只追加的日誌；其他情況保留預設完整解析。

基線和明確全量替換仍需讀取對應來源的完整歷史，未宣稱這兩種路徑已增量化。
