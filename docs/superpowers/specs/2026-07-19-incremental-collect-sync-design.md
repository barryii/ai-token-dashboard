# 增量採集同步(水位線 + 批量寫入)設計

## 背景與問題

資料庫遷移到遠端(Supabase Postgres)後,每次採集的寫入資料庫方式暴露出嚴重 IO 問題:

- `time_usage`:每個資料源先 `DELETE` 該 (device, source) 的全部行,再把 90 天視窗內的事件(目前約 11,500 行)逐行 `INSERT`。
- `daily_usage`(約 379 行)與 `session_usage`(約 618 行):全量逐行 upsert。
- 每條語句一次網路往返,單次採集超過 1.2 萬次往返,對新加坡節點實測約 30 分鐘,並在 Postgres 側產生大量 WAL 與死元組。

根因:`eventKey` 拼入了陣列索引 `index`(`src/collect.mjs`),事件順序變化導致 key 不穩定,無法冪等 upsert,只能刪表重插。

## 相關既有約定:歷史價格鎖定

提交 `f98dd4f`(2026-06-10)已實作 `daily_usage` 的價格鎖定:昨天及更早的行 `cost_usd` 不接受重算,只有當天的行按目前價格更新(`pricing_locked_at` 欄位)。

**缺口**:`time_usage` 因刪表重插,老事件成本每次都按目前價格重算,與日匯總檢視不一致。本設計的增量寫入(老事件永不重寫)自動使 `time_usage` 獲得相同的鎖定語意,無需新增鎖欄位。

## 設計

### 1. 穩定化 eventKey

- 去掉 key 中的陣列索引 `index`。
- 新 key = `client:eventTime:sessionId:model:totalTokens`,批內相同元組按出現順序追加序號(`#0`、`#1`、…)。
- 同一份源日誌重複採集生成完全相同的 key 集合,upsert 冪等。
- key 規則變更意味著與舊資料不相容,首次上線依賴 `--full` 重建(見第 4 節)。

### 2. 水位線增量寫入

- 採集開始時按 (device, source) 查詢遠端 `MAX(event_time)` 作為水位線。
- `time_usage`:只上傳 `eventTime > 水位線 − 48h` 的事件;重疊視窗容忍日誌晚寫,冪等 upsert 保證重疊部分不重複。**不再執行全表 DELETE。**
- `daily_usage`:只 upsert `usageDate >= (水位線 − 48h) 的日期` 的行;更早日期的行 token 與成本均不再變化(成本本就被鎖定)。
- `session_usage`:累計值每次都變,保持全量,但走批量寫。
- 遠端該 (device, source) 無資料時(水位線為空)自動走全量路徑。

### 3. 批量寫入

- 三張表的逐行 upsert 改為多行 `INSERT ... VALUES (...),(...) ON CONFLICT DO UPDATE`,每批 500 行。
- SQLite 與 Postgres 語法一致,MySQL 用 `ON DUPLICATE KEY UPDATE` 多行等價形式;本機與遠端同一套程式碼路徑。
- 網路往返從 1.2 萬次降至 30 次以內。

### 4. `--full` 全量重建

- `node src/collect.mjs --full`:保留「刪除 + 重傳」語意(同樣批量化),用於 key 規則變更、採集器 bug 修復等結構性重建。
- 明確語意:全量重建會按**目前**價格重算歷史事件成本,是有意為之的重置,不是常規操作;價格表日常更新不需要 `--full`。

### 5. 語意變化:遠端保留超窗歷史

去掉全表刪除後,本機日誌滾動清理(超過 90 天)的事件在遠端仍保留。視為功能升級(歷史更完整),不做清理任務。

## 測試

- key 穩定性:同一輸入兩次生成相同 key 集合;重複元組序號正確。
- 水位線過濾:邊界(恰好等於水位線、視窗內、視窗外)行為正確;空遠端走全量。
- 批量 SQL 建構:分批邊界(0 行、1 行、500 行、501 行);三種驅動的語法分支。
- 整合:本機 SQLite 全量採集 → 增量採集,前後行數與聚合值一致;增量不改動老事件 cost_usd。
- 現有 `node --test` 全部通過。

## 非目標

- 不做逐條髒標記/內容雜湊變更檢測(全域性變更由 `--full` 覆蓋,零散變更不存在)。
- 不做遠端超窗資料清理。
- 不做定時採集(使用者目前手動觸發)。
